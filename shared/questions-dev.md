# 개발 질문

요구사항을 읽고, **요구사항에 이미 답이 있는 것은 묻지 않는다.** 남은 것만 묻는다.

## 묻는 방식

- **workflow §2 "묻는 형식"** 대로 — 모든 질문을 선택지 A · B · C … + 기타(직접 입력)로, **권장안을 첫 번째(A)**에 "(권장)" 과 이유 한 줄. 선택형 질문 도구가 있으면 그것으로, 한 묶음 4개까지.
- 아래 표의 열린 질문(예: "누가, 무엇을 하러 오는가")도 요구사항에서 짐작되는 답을 선택지로 만들어 묻는다.
- 사용자가 모르는 개념이 나오면 질문 안에서 한 줄로 풀어 준다.
- 답을 받으면 `docs/04-communication/` 에 질의 기록으로 남긴다 (템플릿 `requirements-clarification.md`).

## 질문 목록

`full` = web-full 에서 묻는다, `lite` = web-lite 에서도 묻는다.

### 목적과 사람
| | 질문 | 왜 묻나 |
|---|---|---|
| full · lite | 누가, 무엇을 하러 오는가 — 첫 화면에서 가장 먼저 해야 할 한 가지 | 화면 우선순위가 여기서 정해진다 |
| full · lite | 성공의 기준 — 무엇이 되면 "됐다"인가 (문의 수, 가입, 공유, 그냥 공개) | 끝을 정한다 |
| full | 기한과 단계 — 먼저 공개할 최소 범위 | 단계 나누기 |

### 기능
| | 질문 | 왜 묻나 |
|---|---|---|
| full · lite | 꼭 있어야 할 기능 / 있으면 좋은 기능 / 이번에는 안 할 기능 | 범위 고정 |
| full | 로그인이 필요한가, 누가 무엇을 볼 수 있나 (권한) | 인증 · 데이터 구조가 갈린다 |
| full · lite | 사용자가 입력하는 것이 있나 (문의 양식, 신청, 업로드) — 입력이 어디로 가야 하나 (메일, 시트, DB) | 저장 · 알림 경로 |
| full | 콘텐츠는 누가, 어디서, 얼마나 자주 바꾸나 (직접 수정, 노트에서 자동, 관리 화면) | 콘텐츠 관리 방식 |
| full | 검색 · 필터 · 목록 정렬이 필요한가 | |
| full | 결제 · 외부 서비스 연동 (지도, 메일, AI, 분석) | 비용 · 키 관리 |

### 운영
| | 질문 | 왜 묻나 |
|---|---|---|
| full · lite | 도메인이 있나, 어디에 올릴까 (무료 호스팅 권장 여부) | 배포 |
| full · lite | 월 비용 상한 (0원이어야 하나) | 기술 선택 |
| full | 언어 (한국어만 / 영어도) | |
| full | 검색 노출(SEO) · 방문 통계가 필요한가 | |
| full | 접근성 기준 (KWCAG · WCAG) — 공공 · 채용 제출용이면 권장 | |
| full · lite | **저장소 공개 여부, 공개라면 `docs/` · 에이전트 설정까지 올릴지** | 공개 저장소 사고 예방 (workflow §6) |
| full | 개인정보 · 회사 정보가 콘텐츠에 섞이나 — 공개 전 거르는 장치가 필요한가 | |

### 제작자가 판단해 먼저 꺼낼 것
요구사항에서 **사용자가 생각하지 못했을 위험**을 찾아 먼저 알린다. 예:
- 공개하면 안 되는 내용이 섞일 수 있는 콘텐츠
- 무료 요금제 한도, 외부 API 비용이 갑자기 늘 수 있는 구조
- 휴대폰에서 무거운 화면 (3D, 큰 이미지)
- 검색 엔진이 읽을 글이 없는 화면

알릴 때는 "위험 → 제안하는 대응 → 고를 것" 순서로 짧게.

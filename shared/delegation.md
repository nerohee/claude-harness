# 작업 맡기기와 검수

계획 · 질문 · 검수는 메인 대화(Opus · high)가, 구현은 작업자 에이전트(Sonnet)가 맡는다.

## 작업자

| 에이전트 | 모델 · 수준 | 맡길 일 |
|---|---|---|
| `harness-builder` | Sonnet · medium | 계획이 구체적인 구현 — 화면 · 컴포넌트, 정해진 API, 설정 파일, 문서 정리, 반복 수정 |
| `harness-builder-deep` | Sonnet · high | 판단이 많이 필요한 구현 — 인증 · 권한, 결제 · 정산, 데이터 이전, 동시성 · 캐시, 원인 모를 버그, 성능 |

- 계획 단계에서 작업마다 담당을 정해 `dev-plan.md` 에 적는다 (`builder` / `deep` / `직접`).
- **직접** 하는 편이 나은 일 — 몇 줄짜리 수정, 사용자와 주고받으며 다듬는 디자인 미세 조정, 검수 중 발견한 작은 고침.
- 같은 파일을 건드리지 않는 작업만 동시에 맡긴다.

## 맡길 때 적는 것 (작업 지시서)

작업자는 이 대화를 모른다. 지시서만 보고 일할 수 있게 쓴다.

```
목표: 한 문장
범위: 만들거나 고칠 파일 · 화면 · API
하지 않을 것: 범위 밖 (다음 단계로 미룬 것)
알아야 할 맥락: 관련 파일 경로, 따라야 할 기존 패턴, 결정 번호(D-xx)
디자인 기준: 쓸 토큰 · 컴포넌트 (화면 작업일 때)
완료 기준: 무엇이 되면 끝인가 — 확인할 수 있는 문장으로
확인 명령: 타입 검사 · 시험 · 빌드 명령
보고 형식: 바꾼 파일 / 한 일 / 확인 명령 결과 원문 요약 / 남은 문제 / 지시와 다르게 한 것과 이유
```

## 검수 (작업자가 돌아온 뒤, 사용자에게 보이기 전)

작업자의 보고를 그대로 믿지 않는다.

1. 바뀐 파일을 직접 읽는다 (`git diff`).
2. 확인 명령을 다시 돌린다.
3. 완료 기준 하나하나를 확인한다.
4. 범위 밖 변경, 지운 시험, 꺼 둔 검사, 하드코딩한 비밀값이 없는지 본다.
5. 모자라면 고칠 점을 적어 같은 작업자에게 다시 맡기거나(이어서), 작으면 직접 고친다.
6. 통과하면 사용자에게 — 화면 작업이면 개발 서버 확인부터.

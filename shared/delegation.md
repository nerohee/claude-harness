# 작업 맡기기와 검수

계획 · 질문 · 최종 검수는 메인 대화(Opus · high)가, 디자인 · 구현 · 시험 · 점검은 작업자 에이전트가 맡는다. 작업자는 사용자와 직접 이야기하지 않고 메인에게만 보고한다.

## 작업자

| 에이전트 | 담당 표기 | 모델 · 수준 | 맡길 일 |
|---|---|---|---|
| `harness-designer` | `designer` | Opus · high | 레퍼런스 조사, 디자인 방향 · 토큰, 시안, 구현된 화면의 디자인 검수 |
| `harness-builder-ui` | `ui` | Sonnet · medium | 고른 시안 · 토큰대로 화면 · 컴포넌트, 화면 상태, 키보드 · 접근성 |
| `harness-builder-system` | `system` | Sonnet · high | API · 서버 · DB, 인증 · 권한, 결제 · 정산, 데이터 이전, 동시성 · 캐시, 앱 시스템 쪽(Rust) · 앱 권한 · 자동 업데이트, 원인 모를 버그, 성능 |
| `harness-tester` | `tester` | Sonnet · medium | 시험 작성 (단위 · 화면 · 전체 흐름), 버그 재현 시험 — 시험 파일만 고친다 |
| `harness-helper` | `helper` | Haiku · low | 문서 정리, 이름 바꾸기, 같은 패턴 반복 수정, 설정 값 옮기기 |
| `harness-reviewer` | `reviewer` | Opus · high | 읽기 전용 점검 — 마감 점검, 위험한 변경의 두 번째 검토 |

성격 · 원칙 · 보고 형식은 각 에이전트 파일(하네스 저장소 `agents/harness-*.md`), 모든 작업자 공통 규칙은 `agents/_common/rules.md` 에 있다. 사람이 읽는 요약은 하네스 README "작업자 프로필". 작업자를 고치거나 늘리는 것은 `/harness-setup` C 절.

## 담당 정하기

계획 단계에서 작업마다 담당을 정해 `dev-plan.md` 에 적는다 (위 담당 표기 또는 `직접`).

- **화면 작업** — `designer`(레퍼런스 · 시안) → 사용자가 고름 → `ui`(구현) → `designer`(디자인 검수) → 메인 검수. 시안이 필요 없는 작은 화면 변경은 `ui` 만.
- **시스템 작업** — `system`. 중요한 흐름(인증 · 결제 · 데이터 이전)은 이어서 `tester` 로 실패 경우 시험을 더한다.
- **버그** — 원인을 모르면 `system`. 재현 시험이 먼저 필요하면 `tester` → `system`.
- **판단이 필요 없는 일** — `helper`. 하다가 판단이 필요해지면 멈추고 돌아오니, 그때 `ui` · `system` 으로.
- **점검** — `reviewer`. 마감 전, 그리고 인증 · 결제 · 데이터 이전 · 앱 권한을 바꾼 단계 뒤.
- **직접** — 몇 줄짜리 수정, 사용자와 주고받으며 다듬는 디자인 미세 조정, 검수 중 발견한 작은 고침.
- `designer` · `reviewer` 는 Opus 라 비싸다. 첫 화면 · 중요한 화면 · 마감처럼 필요한 시점에만.
- 같은 파일을 건드리지 않는 작업만 동시에 맡긴다.
- **예전 표기** — 진행 중인 프로젝트의 `dev-plan.md` 에 `builder` 가 있으면 작업 내용에 따라 `ui` 또는 `system`, `deep` 은 `system` 으로 읽는다. 그 문서를 다음에 고칠 때 새 표기로 바꾼다.

## 맡길 때 적는 것 (작업 지시서)

작업자는 이 대화를 모른다. 지시서만 보고 일할 수 있게 쓴다.

**지시서는 파일로 쓴다** — `docs/02-development/briefs/<단계>-<두 자리 번호>-<짧은 이름>.md` (틀: `templates/brief.md`). 작업자에게는 지시서의 절대 경로와 "이 파일을 읽고 그대로 하라" 를 보낸다. 세션이 끊겨도 같은 지시서로 다시 맡길 수 있다 (workflow §8).

- **작업 항목은 체크 목록**(`- [ ]`)으로. 작업자가 끝낼 때마다 `[x]` 로 바꿔서, 중간에 끊겨도 어디까지 했는지 남는다.
- **한 번에 끝낼 크기로** — 작업 항목 3~7개, 바꿀 파일 대략 5개 안팎. 넘으면 지시서를 나눈다. 끊겼을 때 잃는 양이 줄고, 작업자의 대화도 짧아진다.

```
목표: 한 문장
범위: 만들거나 고칠 파일 · 화면 · API
하지 않을 것: 범위 밖 (다음 단계로 미룬 것)
알아야 할 맥락: 관련 파일 경로, 따라야 할 기존 패턴, 결정 번호(D-xx)
디자인 기준: 쓸 토큰 · 컴포넌트 · 고른 시안 (화면 작업일 때)
작업 항목: 체크 목록 (- [ ]) — 작업자가 끝낼 때마다 [x]
완료 기준: 무엇이 되면 끝인가 — 확인할 수 있는 문장으로
확인 명령: 타입 검사 · 시험 · 빌드 명령 (실패하면 요약 없이 원문을 보고 — rtk 가 있으면 `rtk proxy <명령>`)
보고 형식: 에이전트 파일의 "끝나면" 형식
```

### 맡기는 순서

1. 지시서 파일을 쓴다.
2. `handoff.md` 를 갱신한다 — 진행 중인 작업에 `맡김`, 지금 커밋 번호(`git rev-parse --short HEAD`), 이미 바뀌어 있던 파일(`git status --short`). **맡기기 전에** 쓴다 — 작업자가 일하는 중에 끊기면 이것이 유일한 단서다.
3. 작업자에게 맡긴다.
4. 돌아오면 보고를 지시서 끝 "기록" 에 붙이고 `handoff.md` 를 `돌아옴` 으로.
5. 검수 결과를 지시서 끝에 적고 `handoff.md` 를 `검수 통과` 또는 `다시 맡김` 으로.

작업자별로 더 적는 것:

| 담당 | 더 적는 것 |
|---|---|
| `designer` | 사용자 답 (분위기 단어 · 밝기 · 좋아하는 / 싫어하는 레퍼런스 · 꼭 쓸 색 · 로고), 플랫폼 (웹 / 데스크톱 · 대상 OS), 시안 개수와 들어갈 화면, 일의 종류 (방향 · 시안 / 디자인 검수 — 검수면 비교할 시안 · 화면 · 실행 명령) |
| `tester` | 시험할 흐름 · 조건, 쓸 시험 도구, 버그 재현이면 재현 조건 |
| `reviewer` | 볼 범위 (커밋 범위 · 파일 · 기능), 중점 영역, 이미 알고 있어 빼도 되는 것 |

## 검수 (작업자가 돌아온 뒤, 사용자에게 보이기 전)

작업자의 보고를 그대로 믿지 않는다.

1. 바뀐 파일을 직접 읽는다 (`git diff`).
2. 확인 명령을 다시 돌린다.
   - 명령 출력을 줄여 주는 hook(예: `rtk`)이 있으면 결과가 요약돼 보인다. **실패했거나 오류 원문이 필요할 때는 요약 없이 다시 돌린다** — `rtk proxy <명령>`.
3. 완료 기준 하나하나를 확인한다.
4. 범위 밖 변경, 지운 시험, 꺼 둔 검사, 하드코딩한 비밀값이 없는지 본다.
5. 모자라면 지시서 끝에 "2차 지시" 로 고칠 점을 적어 같은 작업자에게 다시 맡기거나(이어서), 작으면 직접 고친다.
6. 통과하면 사용자에게 — 화면 작업이면 실행 확인부터 (workflow §3).

작업자별로 더 보는 것:

- `designer` — 시안을 직접 띄워 본다. 레퍼런스를 베끼지 않았는지(로고 · 그림 · 문구), 기준(대비 · 글자 크기)을 지켰는지. 그다음 사용자에게 시안을 보이고 고르게 한다.
- `tester` — 앱 코드를 고치지 않았는지, 실패 시험을 건너뛰게 하지 않았는지. 앱 쪽 버그로 보고된 것은 담당을 정해 맡긴다.
- `reviewer` — 찾은 것마다 정말 그런지 직접 확인한 뒤, 고칠 것 · 담당 · 미룰 것을 정해 사용자에게 짧게 보인다. 확인되지 않은 것은 "가능성" 으로 구분한다.

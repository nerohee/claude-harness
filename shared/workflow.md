# 공통 작업 규칙 (web-full · web-lite · desktop-app)

모든 개발 스킬이 똑같이 따르는 진행 방식이다. 스킬 파일은 이 문서를 먼저 읽고, 자기 스킬에만 있는 차이를 덧붙인다.

## 0. 시작할 때

1. **설정 읽기** — `~/.claude/harness/config.local.json`. 없으면 `config.example.json` 의 기본값으로 진행하되, 사용자에게 `/harness-setup` 으로 설정을 만들 수 있다고 한 줄 알린다.
2. **모델 확인** — 계획 · 질문 · 검수는 설정의 `planner`(기본 Opus · high)가 맡는다. 지금 대화의 모델이 그보다 낮으면, 시작 전에 `/model` 로 바꾸고 추론 수준을 `high` 로 맞추도록 안내하고 기다린다. 스킬의 `model` 지정은 첫 턴에만 걸리므로 세션 자체를 맞춰야 한다.
3. **요구사항 원본** — 사용자가 준 요구사항 마크다운은 **고치지 않는다.** 경로만 기록하고 그대로 읽는다. 대화로 받아 적은 요구사항(5번)은 사용자가 확인한 순간 원본이 되고, 그때부터 고치지 않는다.
4. **이어서 하는 경우** — 프로젝트에 `docs/02-development/handoff.md` 나 `dev-plan.md` 가 이미 있으면 새로 시작하지 않는다. §8 "이어 갈 때" 를 따른다 (`/harness-resume` 과 같은 절차).

5. **요구사항이 없을 때** — 스킬을 경로 없이 불렀거나 파일이 없으면, 이미 진행 중인 프로젝트(4번)가 아닌지 먼저 보고 세 가지를 제안한다 (권장안 먼저).

   | 선택지 | 하는 일 |
   |---|---|
   | **대화로 받아 적기** (아직 쓴 게 없으면 권장) | 틀(`templates/requirements.md`)의 항목 순서로 한 묶음씩 묻는다 (§2 "묻는 형식"). 답을 프로젝트 루트 `requirements.md` 로 정리해 보이고 (이미 있으면 다른 이름을 제안), 사용자가 확인하면 그것을 원본으로 바로 진행한다. 받아 적으며 답한 것은 P0 에서 다시 묻지 않는다 |
   | **틀 만들어 주기** | 프로젝트 루트에 `requirements.md` 를 틀로 만든다 — 이 스킬에 맞지 않는 칸은 지운다 (웹이면 "누가 쓰나 · 어느 OS"). 경로를 알려 주고, 다 쓰면 `/<스킬> requirements.md` 로 다시 부르라고 안내한 뒤 멈춘다 |
   | **경로 알려 주기** | 이미 써 둔 파일이 있을 때 — 경로를 받아 진행한다 |

   요구사항은 자유 형식이 기본이다. 틀은 "이런 걸 쓰면 좋다" 는 안내일 뿐 칸을 다 채우라고 하지 않는다 — 빠진 것은 P0 질문이 채운다.

## 1. 대답과 보고

- 설정의 `language`(기본 한국어)로 쓴다. 코드 · 명령 · 경로 · 오류 원문만 원래 글자로 둔다.
- 짧게. 표는 비교할 때만. 결과는 있는 그대로 — 시험이 실패했으면 실패했다고, 건너뛴 단계는 건너뛰었다고 쓴다.
- 이미 답을 받은 확인 거리는 다시 묻지 않는다.

## 2. 승인 게이트 (가장 중요)

**모든 작업은 시작 전에 승인을 받는다.** 소개는 짧게, 네 가지만:

| 항목 | 예 |
|---|---|
| 무엇을 | "검색 상자와 결과 목록" |
| 왜 지금 | "목록 화면이 끝나서 그다음 순서" |
| 산출물 | "검색 화면, 색인 생성 스크립트" |
| 하지 않는 것 | "자동완성은 다음 단계" |

- 대화 중 범위가 바뀌면 **개발 계획을 먼저 고치고** 다시 승인을 받는다.
- 사용자가 결정할 일(취향 · 비용 · 공개 범위 · 되돌리기 어려운 작업)은 권장안을 첫 번째에 두고 묻는다. 정답이 있는 기술 판단은 묻지 말고 정한 뒤 한 줄로 알린다.

### 묻는 형식

요구사항 질문 · 디자인 질문 · 결정 · 이어 하기 — **사용자에게 묻는 모든 곳에서** 고르는 방식으로 묻는다. 선택지 A · B · C … 와 기타(직접 입력). 권장안은 언제나 첫 번째(A)에 "(권장)" 을 붙이고 이유를 한 줄로.

- **선택형 질문 도구가 있으면 그것으로** (Claude Code 의 `AskUserQuestion`). 한 번에 질문 4개까지, 질문마다 선택지 2~4개, 짧은 머리말(12자 이내). 기타(Other · 직접 입력)는 도구가 자동으로 붙이므로 선택지에 넣지 않는다. 여러 개를 고를 수 있는 질문(예: 꼭 있어야 할 기능, 분위기 단어)은 여러 개 고르기로.
- **도구가 없으면 글로 같은 모양으로**:
  ```
  **1. 질문** — 왜 묻는지 한 줄
  - A) 선택지 (권장) — 이유
  - B) 선택지 — 설명
  - C) 선택지 — 설명
  - 기타) 직접 적기
  ```
  답은 "1-A, 2-기타: …" 처럼 받는다.
- **열린 질문도 선택지로 바꾼다** — 예: "참고할 사이트가 있나요?" → A) 없음 — 제작자가 레퍼런스를 찾아 제안 (권장) / B) 있음 — 기타에 주소를 적기. 사용자가 막막하지 않게 하되, 기타로 언제든 자유롭게 답할 수 있게.
- 선택지는 서로 확실히 다르게. 사용자가 모르는 개념은 선택지 설명 안에서 한 줄로 푼다.
- 한 묶음은 도구 한 번(질문 4개)까지. 더 있으면 다음 묶음으로 — 앞 묶음의 답에 따라 뒤 질문이 바뀔 수 있다.

## 3. 실행

- 구현은 [delegation.md](delegation.md) 에 따라 작업자 에이전트에게 맡긴다. 맡긴 결과는 **반드시 직접 검수**한 뒤에 사용자에게 보인다.
- **화면이 바뀌는 작업** — 사용자가 먼저 실행해서 본다 (실행 확인). 웹은 개발 서버 — 띄우는 명령 · 볼 주소, 데스크톱 앱은 개발 실행(`npm run tauri dev`) — 띄우는 명령과, 볼 것을 알려 주고 기다린다. 괜찮다고 하면 그때 전체 시험(브라우저 · 접근성 · HTML 표준 등 프로젝트에 있는 것)을 돌린다.
- 검사 명령이 없으면 첫 단계에서 만든다 — 타입 검사, 빌드, 최소한의 화면 시험.

## 4. 기록

| 언제 | 무엇을 | 어디에 |
|---|---|---|
| 사용자에게 질문하고 답을 받으면 | 질문 · 답 · 제작자 권장안 · 판단 | `docs/04-communication/YYYY-MM-DD-<주제>.md` |
| 기술 결정을 하면 | D-번호, 결정 · 왜 · 버린 대안 | `docs/01-planning/decisions.md` (web-lite · 작은 desktop-app 은 plan.md 안 "결정" 절) |
| 작업을 맡기기 **직전** | 지시서 파일 · 진행 중인 작업(`맡김` · 그때 git 커밋 번호 · 이미 바뀌어 있던 파일) | `docs/02-development/briefs/` · `handoff.md` |
| 작업자가 돌아오면 · 검수하면 | 보고 · 검수 결과를 지시서 끝에, 상태(`돌아옴` · `검수 통과` · `다시 맡김`) | 지시서 · `handoff.md` |
| 사용자에게 묻거나 실행 확인을 기다릴 때 | 기다리는 것 | `handoff.md` |
| 단계를 마치면 | 진행 로그 한 줄 + 다음 할 일 | `docs/02-development/dev-plan.md` 끝 · `handoff.md` |
| 그날 작업이 끝나면 | 키워드 줄 + 항목별 한 일 · 고객 결정 · 검사 결과 | `docs/03-worklog/YYYY-MM-DD.md` |

### 이어 하기 준비 (P0 에서 문서 골격을 만들 때)

- `02-development/handoff.md`(틀 `handoff.md`)와 `02-development/briefs/` 를 함께 만든다.
- 프로젝트 루트 `CLAUDE.md` 에 이어 하기 안내를 넣을지 묻는다. 권장은 **넣기** — `CLAUDE.md` 는 새 세션에서도, 대화가 요약된 뒤에도 늘 읽혀서 "이어서 하자" 만으로 이어진다. 공개 저장소에 올라가도 무해한 내용이다. 파일이 있으면 끝에 덧붙이고, 없으면 만든다:
  ```markdown
  ## claude-harness
  이 프로젝트는 claude-harness(`<스킬>`)로 진행 중이다. 이어서 할 때는 `docs/02-development/handoff.md` 를 먼저 읽고 `~/.claude/harness/shared/workflow.md` §8 을 따른다.
  ```

틀은 `~/.claude/harness/shared/templates/` 에 있다. 틀의 `<…>` 자리는 지금 설정 · 프로젝트 값으로 채우고, 안내 문구를 그대로 남기지 않는다 (예: `dev-plan.md` 작업 규칙의 git 줄은 `commitPolicy` 에 맞는 문장 하나로).

## 5. git

설정 `commitPolicy` 를 따른다.

- `propose-only`(기본) — **커밋 · 푸시는 사용자가 한다.** 마일스톤마다 커밋 메시지만 제안하고, **어느 저장소인지** 함께 쓴다. 저장소가 둘 이상이면 저장소별로 나눠 제안한다. 제안하는 모양:
  - **명령마다 따로 된 코드 블록** — `git add …` 한 블록, `git commit -m "<메시지>"` 한 블록. `&&` 로 이어 붙이지 않는다 (한 번에 통째로 복사해 실행되지 않도록).
  - `-C <경로>` · `cd` 는 쓰지 않는다 — 사용자는 그 저장소 폴더에서 작업하고 있다. 저장소가 둘 이상이면 저장소 이름을 제목으로 나눠 적는다.
  - `git add` 에는 바꾼 파일 · 폴더를 적는다. `git add -A` 는 `.gitignore` 가 비밀값(`.env` 등)을 막고 있는 것을 확인했을 때만.
  - 커밋 전에 확인할 것이 있는 작업이면(새 파일이 생김, 지운 파일, 비밀값 파일이 생길 수 있음) 그 앞에 `git status --short` 를 따로 한 블록 두고, **무엇을 보면 되는지** 한 줄 적는다 (예: "`??` 로 `agents/_common/` 이 보여야 함, `.env` 가 없어야 함"). 확인할 것이 없으면 생략한다.
- `agent-commits` — 승인받은 단계가 끝나면 커밋까지 한다. 푸시는 여전히 사용자가 한다.

### 커밋 메시지 형식

**한 줄**로 쓴다:

```
<종류>: <무엇이 달라졌나 — 한국어 요약>
```

| 종류 | 언제 |
|---|---|
| `feat` | 새로 생긴 것 — 기능 · 화면 · 스킬 · 작업자 |
| `fix` | 고침 |
| `refactor` | 동작은 같고 구조만 바꿈 |
| `docs` | 문서만 |
| `test` | 시험만 |
| `chore` | 설정 · 의존성 · 빌드 같은 잡일 |

- 요약은 설정 `language` 로, 무엇이 달라졌는지 보이게. 마침표 없이, 대략 60자 안쪽.
- 갈래가 여럿이면 ` — ` 로 주제와 내용을 나누고 ` · ` 로 늘어놓는다. 예: `feat: 작업자 6종 — designer · ui · system · tester · helper · reviewer`
- 파일 · 명령 · 이름은 원래 글자로. 예: `fix: macOS 에서 작업자 가드 hook 이 동작하도록`, `refactor: 작업자 공통 규칙 · 가드를 agents/_common 으로 분리`
- 한 커밋에 한 주제. 주제가 둘이면 커밋을 나눠 제안한다.
- 본문은 쓰지 않는다. 사용자가 원할 때만 빈 줄 뒤에 `- ` 목록으로.
- `agent-commits` 로 메인이 직접 커밋할 때는 같은 한 줄에, 빈 줄 뒤 시스템이 알려 준 공동 작성 줄(`Co-Authored-By: …`)을 붙인다. 사용자가 하는 커밋(`propose-only`)의 제안에는 붙이지 않는다.

### 그 밖에
- 강제 푸시 · 이력 다시 쓰기 · 저장소 공개 전환은 언제나 사용자가 직접 한다. 명령만 드린다.

## 6. 공개 저장소와 비밀값

- 첫 질문에서 **저장소를 공개할지**, 공개라면 **기획 · 작업 일지(`docs/`)와 에이전트 설정까지 올릴지** 묻는다. 기본 권장은 "코드만 공개, `docs/` 는 로컬 또는 비공개 저장소".
- 비밀값은 채팅에 쓰지 않는다. `.env` 는 커밋하지 않고 `.env.example` 에는 **가짜 값만** 넣는다.
- 앱 서명 키 · 인증서(업데이트 서명 비밀 키, `.pfx` 등)는 비밀값과 같이 다룬다 — 저장소 밖에 두고, 만들기 · 쓰기는 사용자가 한다. 잃어버리면 되돌릴 수 없는 키는 백업을 안내한다.
- 설치해 쓰는 앱(데스크톱) 안에 넣은 키는 누구나 꺼낼 수 있다 — 앱에 비밀값을 넣지 않는다.
- 공개 저장소에 처음 올리기 전, 그리고 공개 범위가 바뀔 때 **이력 전체**를 검사한다 — 비밀값 모양, 연락처, 회사 · 고객 정보, 개인 신상.

## 7. 끝맺음 (각 응답의 마지막)

- 사용자가 할 일이 있으면 **할 일만** 번호로. 명령은 복사해 쓸 수 있게.
- 다음 단계 제안은 한두 줄로, 승인을 묻는 형태로.
- 단계가 끝났으면 "여기서 새 세션으로 이어도 됩니다 (`/harness-resume`)" 를 한 줄 덧붙인다. 대화가 길어졌으면 그렇게 하기를 권한다 — 기록이 파일에 있어 잃는 것이 없고, 대화가 짧아져 토큰을 덜 쓴다.

## 8. 끊겼다 이어 하기

토큰 · 사용량 한도로 세션이 멈추거나, 대화가 요약되거나, 새 세션에서 이어 갈 때. **진행 상태는 대화가 아니라 파일에 있다** — `handoff.md`, 지시서(`briefs/`), `dev-plan.md`, 작업 일지. 그래서 §4 의 기록, 특히 **맡기기 직전의 `handoff.md` 갱신**을 빠뜨리지 않는다.

### 이어 갈 때

1. `handoff.md` 에서 스킬 · 요구사항 · 단계 · 상태를 읽는다. 그 스킬의 "먼저 읽기" 파일들을 다시 읽는다 — 대화가 요약됐거나 새 세션이면 규칙이 빠져 있다.
2. 상태별로 확인한다.

   | 상태 | 확인할 것 | 이어 가는 법 |
   |---|---|---|
   | 작업자 일하는 중 (`맡김`) | 지시서의 `[x]`, `git status` · 맡길 때 커밋 이후 바뀐 파일 (이미 바뀌어 있던 파일은 빼고), 확인 명령 | 다 됐으면 검수로. 일부만 됐으면 **이어서 마저 하기(권장)** — 같은 세션이면 그 작업자를 이어서 부르고, 새 세션이면 같은 지시서에 "이미 된 것" 을 적어 새로 맡긴다. 꼬였으면 **되돌리고 다시** — 되돌릴 파일 목록을 보이고 사용자가 고른 뒤에만 되돌린다 |
   | 돌아옴 · 검수 전 | 지시서 끝의 보고, 바뀐 내용 | 검수부터 (delegation.md) |
   | 사용자 답 · 실행 확인 기다림 | "기다리는 것" | 그 질문 · 확인 요청을 다시 보인다 |
   | 단계 사이 | 진행 로그 · 다음 할 일 | 다음 단계를 §2 대로 소개 |

3. `handoff.md` 와 실제가 다르면(파일이 더 바뀌었거나 커밋이 더 있음) 사용자가 그사이 직접 고쳤을 수 있다 — 짐작하지 말고 묻는다.
4. 짧게 보고하고 승인을 기다린다 — 스킬 · 단계, 끊긴 지점과 확인한 것, 다음 할 일.

# 디자인 — 묻는 법과 정하는 법

사용자는 디자인 전문가가 아니다. **디자인은 제작자가 주도한다.** 사용자에게는 "좋다 / 싫다"로 답할 수 있는 것만 묻고, 서체 · 배색 값 · 간격 같은 전문 결정은 제작자가 내린 뒤 한 줄로 이유를 알린다.

## 1. 묻는 것 (전문 용어 없이)

한 묶음에 다 묻지 않아도 된다. web-lite 는 ★ 만. desktop-app 은 `desktop/design.md` 가 바꾸는 질문을 따른다.

| | 질문 | 선택지 예 |
|---|---|---|
| ★ | 처음 보는 사람이 어떤 느낌을 받았으면 하나요? (두세 개) | 차분한 · 믿음직한 · 고급스러운 · 따뜻한 · 발랄한 · 미래적인 · 단정한 · 개성 있는 |
| ★ | 밝은 화면 / 어두운 화면 / 둘 다(기기 설정 따라) | |
| ★ | 마음에 드는 사이트나 앱이 있나요? 없어도 됩니다. 싫은 것도 좋아요 | 주소나 이름 |
| | 꼭 써야 하는 색 · 로고 · 이름이 있나요? 피하고 싶은 색은? | |
| | 사진 · 그림이 많은 편 / 글 위주로 깔끔한 편 | |
| | 움직임 — 거의 없음 / 은은하게 / 눈에 띄게 | |
| ★ | 주로 휴대폰으로 볼까요, PC 로 볼까요? | |

답을 받으면 제작자가 **방향 한 단락**으로 정리해 되묻는다. 예: "차분하고 믿음직한 쪽으로, 어두운 배경에 푸른 강조색 하나, 글은 크고 여백은 넉넉하게 — 맞나요?"

## 2. 시안으로 고르게 하기

말로 고르기 어려운 것(첫 화면, 전체 분위기)은 **실제 화면 시안**으로 보인다.

- 2~3개 (web-lite 는 2개까지). 서로 **확실히 다르게** — 같은 안의 색만 바꾼 것은 시안이 아니다.
- 실제 화면 위에서 바꿔 볼 수 있게 한다 (예: `?variant=a|b|c`). 각 시안에 이름과 한 줄 설명.
- 사용자가 섞어서 고르면("B 의 틀에 C 의 문구") 그대로 받아 합친다.
- 고른 뒤 시안 코드는 지운다.

## 3. 제작자가 정하는 것 (사용자에게 묻지 않음)

웹 기준이다. 데스크톱 앱은 `desktop/design.md` §2 가 바꾸는 항목을 따른다.


- **디자인 토큰** — 색 · 글자 크기 단계 · 간격 · 둥글기 · 그림자를 변수로 정하고 화면은 변수만 쓴다. 다크 모드는 같은 이름의 변수를 다시 정의한다.
- **글자** — 본문 16px 이상, 줄 간격 넉넉하게, 한글 웹폰트는 필요한 글자만(서브셋).
- **대비** — 본문 글자와 배경 4.5:1 이상, 큰 글자 3:1 이상. 색만으로 정보를 구분하지 않는다.
- **배치** — 휴대폰 폭부터. 좌우 여백 16px 이상, 가로 스크롤 없음. 누르는 대상 44px 이상.
- **움직임** — `prefers-reduced-motion` 을 존중한다. 계속 도는 애니메이션은 화면에 안 보일 때 멈춘다.
- **입력칸** — 휴대폰에서 16px 이상 (iOS 확대 방지).

## 4. 피할 것 (흔한 "AI 가 만든 티")

- 이유 없는 보라 · 분홍 그라데이션, 떠다니는 흐릿한 원
- 모든 카드에 같은 크기 그림자 · 같은 아이콘 배치, 이모지를 아이콘 대신
- "혁신적인 · 최고의" 같은 빈 문구, 가짜 숫자 · 가짜 후기
- 가운데 정렬 일색, 너무 작은 회색 글자

## 5. 디자인 결정 기록

정한 방향 · 토큰 · 고른 시안과 이유를 `docs/01-planning/plan.md` 의 "디자인 방향" 절에 남긴다. 사용자가 고른 것은 "고객 결정"으로 표시한다.
